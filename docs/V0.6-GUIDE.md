# CGPanel 0.6: AI clients, Database Studio and performance

## Connect Claude, ChatGPT or another MCP client

MCP connects a client to your panel tools; it does not run an AI model or include a model subscription. Both administrators and ordinary users have **AI connections · MCP**. Every credential inherits its owner's current account permissions and IP restrictions. Suspended accounts cannot use it.

Owners: serve the panel through a trusted HTTPS certificate. Configure its canonical origin in a systemd override (replace the example with your actual panel origin):

```ini
# systemctl edit cgpanel
[Service]
Environment=CGPANEL_PUBLIC_URL=https://panel.example.com
```

Run `systemctl daemon-reload && systemctl restart cgpanel`. Keep port 2082 on loopback behind Nginx. Permit `/mcp`, `/oauth/*` and `/.well-known/*` through the existing HTTPS panel proxy. Do not expose the broker Unix socket, use insecure-local mode on a public listener, or put credentials in URLs. OAuth public metadata advertises the configured origin rather than trusting incoming Host headers.

Users: open your MCP-capable client's remote connector settings and enter `https://panel.example.com/mcp`. Choose OAuth when supported. Sign into CGPanel, inspect the redirect destination and requested permissions, and explicitly authorize the client. CGPanel uses exact registered redirect URIs, short-lived one-use authorization codes and S256 PKCE. OAuth credentials expire after one day; reconnect when expired. Revoke access under **AI connections · MCP**. Refresh tokens are not implemented.

- **ChatGPT:** in a plan/workspace that supports developer-mode custom MCP apps, create a remote app for the URL above and choose OAuth. Client availability and organization policies vary. Ordinary chat text is not an MCP connection.
- **Claude:** add a custom remote connector in a supported Claude client and use the same URL and OAuth flow. Claude Code and other clients with HTTP header configuration can also use a manual credential.
- **Other clients/model applications:** use MCP Streamable HTTP with JSON responses. The server negotiates protocol `2025-03-26`; it does not provide a stdio executable or legacy SSE transport.

For a client that supports custom headers, create a named credential in CGPanel. Choose **Read only** unless application restarts are required, choose a short expiry, and optionally restrict source IPs/CIDRs. Save the credential in your client's secure secret/environment storage; send `Authorization: Bearer <credential>` on MCP requests. It is shown once, stored as a SHA-256 hash, and cannot be used as an administrator API token. Never paste a real token into an AI conversation, issue, command history, source file, screenshot or public configuration.

Available tools: `list_resources` (apps/domains/databases, credentials excluded), `website_analytics` (owned domain aggregates), and `restart_application` (manage scope only). There is deliberately no arbitrary SQL, host shell or token-creation tool. Administrators see their permitted server resources; users see their own resources. Tool results may contain untrusted tenant names and paths; clients must treat them as data. Ask before restarting a workload.

## Panel login security

Owners open **Panel login security** to enable the one-use, IP-bound arithmetic challenge and set the attempt threshold/window. Both account and source-IP counters persist in SQLite across restarts. Local arithmetic is a basic bot obstacle, not a sophisticated CAPTCHA provider. Website CAPTCHA provider settings remain separate. Keep MFA and source-network restrictions enabled where appropriate.

If a challenge configuration locks out the owner, temporarily set `CGPANEL_LOGIN_RECOVERY=1` on the panel service and restart it. This disables challenges only, not attempt limits. Remove the override after recovery. Limits expire automatically after the configured window.

## Website analytics and security signals

Enable analytics and click tracking under **Website monitoring → Configure**. Copy the tracking snippet into the shared layout of every page to be measured, before `</head>` or `</body>`. Client-side `pushState`, `replaceState` path changes and browser history navigation are tracked. Install the snippet once per page. CGPanel does not inject tracking into arbitrary tenant responses.

The snippet's `data-pointer="true"` enables sampled mouse movement in addition to clicks. Select **Clicks** or **Mouse movement** in Analytics, a page path, and desktop/mobile viewport. Movement is capped at 20 samples per page load, spaced by at least three seconds; no form values, page text or keystrokes are collected. Use explicit non-sensitive `data-cgp-label` attributes for button labels. DNT/GPC opt-outs apply. Consent remains the site owner's responsibility; do not load the tracker until your site's required consent has been given. Keys in tracking snippets identify a site and are not panel credentials.

Monitoring includes sampled request/rejection counts and account-specific failed database logins from the broker's system journal. Configure the request threshold and enable security alerts. Samples cover five minutes, capped at 2,000 Nginx requests and 5,000 journal lines. Save website protection once to enable its access log. Failed-logins require MariaDB/PostgreSQL to actually write the relevant role names to the journal; **coverage unavailable** or zero observed failures does not prove absence of unauthorized access. The feature does not inspect successful SQL, sniff traffic or prove DDoS attacks. Arrange upstream volumetric protection separately.

Alongside Telegram, configure an enabled sender mailbox on the monitored domain (or its parent domain) and one recipient. The broker verifies mailbox ownership and submits notifications through local Postfix. Availability alerts are sent on outage/recovery transitions; suspected-abuse alerts have a one-hour cooldown. Check Background jobs for delivery failures. Local MTA acceptance is not confirmation of remote delivery. Test MX/SPF/DKIM/DMARC, TLS, provider PTR and outbound SMTP on the actual hosting server before depending on email notifications.

## Database Studio

Create a database under **Databases**, then open **Database Studio**. Select it and use **List tables**, **Schema**, or the SQL editor. You can create/alter/drop tables, insert/update/delete rows and execute database-specific SQL using the database's own role. Changes require an explicit confirmation in the browser. Server ownership checks apply to every request; credentials are passed to the local helper on stdin and never sent to the browser.

One statement per request, a 15-second engine timeout, 500 returned rows and a 1 MiB result limit apply. The helper also has a 512 MiB address-space limit and a 25-second wall-clock limit. Truncated transactional statements are rolled back; DDL/nontransactional storage engines may auto-commit. Back up before changes. Export the current result as CSV. For full SQL backup/restore, large imports, account/grant administration, procedures and advanced phpMyAdmin workflows use a database client or the panel backup tools. This is a simplified SQL workspace, not complete phpMyAdmin feature parity. Treat CSV data as untrusted when opening it in a spreadsheet.

## Application ports, private services and resources

Choose a container listening port when creating an application, including 80 or 443. This is an **internal HTTP port**: Nginx terminates public HTTPS and proxies to an automatically assigned loopback host port. Do not run TLS inside the application on port 443 without a separately configured TLS upstream. Starter commands use the selected port, and the container receives `PORT`. Custom commands must honor it. PHP-FPM runtime launchers also honor `PORT` after the updated runtime is rebuilt.

**Private service** runs without a published host port and cannot be attached to a public domain. Apps without an enforced egress gateway use an account-specific rootless bridge. Containers receive private addresses and resolve peers by `cgp_<application-id>` inside that account's network. A web app can call an AI/private service at `http://cgp_<id>:<port>`. Same listening ports are safe in separate containers. Other tenant namespaces have separate bridges; these addresses are not public host listeners. Private services can make outbound requests; private means inbound access is local to the account, not an egress firewall. Applications using an enforced SOCKS gateway keep their separate gateway namespace.

Resource budgets determine application RAM, CPU quota and workspace capacity. `1000` millicores is one CPU core, `4000` permits up to four cores. The old UI assumptions of one CPU / 512 MiB are defaults, not fixed per-app limits. Account budgets can grant larger allocations; unused allocations and IDE overhead are included in budget checks. CPU quotas let multithreaded/multiprocess code use multiple cores; CGPanel cannot make single-threaded code parallel automatically. In **Applications → Performance**, use the assigned-core guidance to configure framework workers (e.g. Gunicorn workers, Node cluster/worker_threads, or a native thread pool) and measure memory per worker before increasing concurrency.

CPU/RAM changes on an enforced volume use Podman update without intentionally stopping an already running application. Disk migration/growth can stop the affected application and file-transfer access. Shrinking is rejected before stopping a workload. A stopped app is returned to its stopped state after applying limits.

Workspace budget promises are checked against physical free storage, including other tenants' unmaterialized promises. Volume images reserve disk blocks. Creation and growth preserve at least 10% or 2 GiB (whichever is larger) for system/recovery use. Budget status exposes free/reserved storage and pressure. Legacy oversized promises are not silently reduced; owners must reconcile them. Database/mail data, images, backups and logs still consume host storage independently, so this is not a guarantee against all disk exhaustion. Monitor host storage and retain off-host backups. Kernel volume limits contain a full application workspace without intentionally stopping unrelated tenants.

## Public-page cache

Enable it under **Applications → Performance**. Nginx only caches eligible GET/HEAD responses explicitly marked `Cache-Control: public` by the application. Cookie/Authorization requests bypass it; `private`, `no-store`, `no-cache` or Set-Cookie responses are excluded. Origin cache headers control expiry; the fallback is 30 seconds. Nginx coalesces concurrent fills and requires repeated access before storing pages. The shared cache is bounded to 256 MiB, with 30-minute inactive eviction. Use versioned assets and suitable cache lifetimes; never mark personalized responses public. `X-CGPanel-Cache` reports HIT/MISS/BYPASS when enabled. Compression and arbitrary HTML-based caching heuristics are not automatically forced onto tenant applications.

## Domains, mail DNS and updates

Hostnames are grouped under the highest assigned ancestor belonging to the same tenant; CGPanel does not guess registrable roots from the last two labels. Subdomain mappings keep independent routing/TLS/policies but share that parent's authoritative zone. Child records and ACME challenges use relative names; remove children before deleting the parent. Parent/child domains cannot be split across tenant accounts. TXT data supports DKIM/DMARC semicolons and is split into DNS character strings of at most 255 bytes. Export a child hostname's zone to obtain its parent zone.

The existing **Panel updates** page controls manual and automatic stable releases (six-hour checks). Updates verify checksums, make a recovery snapshot, defer while background jobs are running, replace panel/broker binaries and check health with rollback on failure. Dependency packages are prepared before the panel is stopped. Application containers and Nginx are separate services and are not intentionally stopped by a panel update. Crash restarts use `unless-stopped` for newly created/recreated applications.

A sub-minute panel interruption and uninterrupted websites are operational targets, not validated guarantees: package maintainer actions, foreground broker operations, migrations, server load and failures can extend downtime. Existing containers retain their old restart policy until recreated. Use a dedicated staging server to measure an update under load before enabling automatic installation in production.
