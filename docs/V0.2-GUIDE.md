# Monitoring, backups, HTTPS, and proxy routing

## Upgrade

On an existing Ubuntu 24.04 CGPanel host, build the frontend (`npm ci --ignore-scripts && npm run build:css`) and run `bash deploy/upgrade-v0.2.sh` as root with Cargo on PATH. The upgrade adds tables to SQLite, retains existing accounts and resources, and saves the previous binaries, registry, configuration, and a consistent SQLite snapshot under `/var/backups/cgpanel-upgrade-*`. It installs a separate Certbot virtual environment, rclone, and a rootless gateway image. It does not replace database grants or the host firewall.

Review `systemctl status cgpanel cgpanel-agent cgpanel-certbot.timer` and the Jobs page after upgrade. Operations interrupted by a panel restart are explicitly marked interrupted. For rollback, stop both panel services, restore the matching database, root registry and binaries from the snapshot, then restart the services. Preserve subsequent tenant changes before rolling back. Restoring binaries alone does not undo provisioning changes.

## Website monitoring and analytics

Assign a domain to an application, open **Website monitoring**, and enable checks. Choose HTTP or HTTPS, a path, a 60–3600 second interval, and optionally a Telegram integration. Two consecutive failed checks open an outage; a successful response resolves it. HTTP 200–399 after bounded redirects is considered available. A check runs from the hosting server, so this does not measure reachability from every country or detect a total outage of the monitoring host itself.

For alerts, create a bot with BotFather, start a chat with it or add it to a group, and save its token and chat ID in **Integrations**. The Test button sends a connection message to that chat. Tokens are kept in the root-owned registry and omitted from API reads. Telegram alert delivery retries three times; final failures appear in Jobs. Proxy routing is optional per integration.

Enable analytics and click tracking separately, then copy the script from **Website analytics → Tracking setup** into each page. Serve it through the supplied same-origin `/__cgpanel/` route. Load it after any consent required by your website. SPA routers can call `window.CGPanelAnalytics.page()` after navigation. `popstate` is tracked automatically; avoid emitting the same view twice.

The dashboard shows daily page views, daily unique IP estimates, popular page paths, referring hostnames, labeled click counts, and a 10 × 20 click-density grid split by mobile/desktop. `data-cgp-label="pricing-button"` supplies a stable label. Positions are normalized relative to viewport width and total page height; changing layouts affects the interpretation of past positions. The grid is an aggregate heatmap, not a screenshot or session replay.

Analytics stores salted hashes scoped to a site and UTC day, not raw IP addresses. It strips query strings/fragments and retains no form contents, keystrokes, full referrer URLs, or arbitrary page text. Do Not Track is respected. Retention is 1–30 days. Limits are 120 events per IP/site/minute and 100,000 per site/day; the browser tracker also bounds events per page. Shared IPs can combine visitors, changing IPs can count one person twice, and daily counts cannot identify a person across days. Public tracking endpoints cannot eliminate fabricated traffic.

**Run SEO check** reports the fetched page's title, description, canonical URL, headings, image alt attributes, document language, viewport, Open Graph title, robots directive, robots.txt and sitemap.xml availability. It does not execute client JavaScript or predict rankings.

## Crontab

**Scheduled tasks** accepts five numeric cron fields, lists, ranges, and steps, plus an IANA timezone such as `Asia/Tehran`. Example: `*/15 9-17 * * 1-5`. `hourly`, `daily`, and `weekly` remain supported. Day-of-month and weekday are ORed when both are restricted. Missing times during a daylight-saving transition are skipped; a repeated wall-clock minute can run twice. Missed occurrences are coalesced after downtime.

Commands run as the container's unprivileged UID 1000 with a 25-second limit. Each task retains the last 20 outcomes and up to 4096 output characters. This is application scheduling; tenants cannot write root's crontab.

## Full .cgp archives

In **Full backups**, select an application, explicitly select its databases, and optionally select up to five storage destinations. CGPanel pauses the application by default, captures files and logical SQL dumps, resumes the application, writes the local archive, then delivers it to storage. Disable pausing only when your application tolerates a live file copy. Each SQL dump has its own consistency boundary; separate databases are not one distributed transaction.

A `.cgp` is an ordinary ZIP with:

- `manifest.json`: format version, owner/application identity, application environment, database metadata, associated domains, DNS records, schedules, and SHA-256 checksums.
- `files/workspace.tar.gz`: the complete application workspace.
- `sql/<database-id>.sql`: one MariaDB or PostgreSQL logical dump per selected database.

Archives contain secrets, including environment variables and database credentials. They are not encrypted at rest. Keep copies only in storage you control; use encrypted disks or provider-side encryption where needed. TLS and pinned SSH host keys protect supported remote transfers. Host operating-system packages, global panel accounts, other applications, unrelated databases, and certificate private keys are outside this per-website archive. Certificates can be reissued.

Downloads require an authorized panel session. A failed remote transfer leaves the local copy available; use **Send** to retry. Scheduled backups use the same cron/timezone syntax, avoid overlapping backups for one application, and keep 1–30 successful local copies. Retention runs only after all requested deliveries succeed. Remote retention is controlled by the storage provider. Individual commands time out, and archive input is bounded to 20 GiB. Monitor disk capacity: this alpha still lacks per-tenant disk quotas.

**Restore** validates manifest checksums and ownership, stops the application, overlays workspace files, and restores the selected databases using their existing restricted database accounts. Newer files absent from the archive remain. Existing database identities and domain assignments must still exist. Domain/DNS/application settings are included in the manifest for administrator recovery; the UI restore does not reassign domains, import archives from another server, or replace current routing/environment configuration. This prevents a former domain owner from restoring revoked assignments. Keep a current backup before overwriting data.

### Remote storage

- **Telegram:** ordinary archives are sent as documents. Files larger than 45 MiB are split into numbered binary parts, followed by a JSON reconstruction manifest with per-part and whole-file hashes. Concatenate in the listed order and verify SHA-256 before opening the resulting `.cgp`.
- **S3:** use an HTTPS origin, bucket, region, access key, secret key, and optional prefix. Uploads use AWS Signature V4, path-style URLs, 8 MiB multipart parts, retries, and abort on failure. Use the endpoint for the bucket's region. A custom CA certificate is supported without disabling TLS verification. Temporary AWS session credentials are not supported in this version.
- **SSH:** supply an absolute destination directory, dedicated unencrypted OpenSSH private key, and a verified server host key (`ssh-ed25519 AAAA…`). SFTP uploads verify that pinned key. Obtain it from the destination administrator through a trusted channel. Testing S3 or SSH uploads a small connection-test archive which you can remove later.

## Free HTTPS and CDN

**Certificates & CDN** offers Let's Encrypt HTTP-01, DNS-01 through local authoritative BIND, and DNS-01 through Cloudflare. HTTP validation requires public port 80 and DNS pointing to this server. Local DNS validation requires registrar delegation to this authoritative server. Cloudflare validation requires a token scoped to DNS editing for the relevant zone. The panel asks for contact email and agreement before requesting a certificate.

The administrator can also request a short-lived certificate for the panel's public IP using Certbot's IP-address support. This uses HTTP validation; DNS-01 does not validate an IP address. Certbot 5.4 or newer is required; the installer supplies a separate virtual environment. `cgpanel-certbot.timer` checks renewal every six hours and reloads Nginx after successful renewal. The certificate page shows expiry details and the last renewal service result. Inspect `/var/log/letsencrypt/letsencrypt.log` for failures.

Staging requests use separate certificate names and do not replace the active certificate. Their certificates are not browser-trusted. No certificate can be issued before ownership/reachability and agreement requirements are met.

Download a BIND zone file and import it into Cloudflare or another DNS provider. Update nameservers and activate CDN proxying at that provider. Cloudflare mode accepts visitor-IP headers only from the bundled published Cloudflare CIDRs; direct requests cannot spoof those headers. Refresh `deploy/cloudflare-realip.conf` against Cloudflare's official IP list when it changes. Other CDNs need an administrator-reviewed trusted-proxy configuration. Zone export does not synchronize later edits automatically. Use Cloudflare Full (strict) after installing a valid origin certificate.

## Enforced SOCKS5 egress

Save a SOCKS5 integration (`socks5h://username:password@host:port`), then select it in **Outgoing traffic → Proxy settings**. Administrators may lock that application's selection. Applying a change recreates the application container, retaining its workspace, environment and web port, with a brief interruption.

A separate rootless gateway shares only the application's network/user namespace. The app remains UID 1000 with no capabilities. The gateway redirects its TCP sockets to Rust SOCKS5 relays and forwards ordinary UDP DNS queries over a SOCKS TCP connection. Therefore a normal PHP `file_get_contents('http://api.myip.com')` uses the configured proxy without application proxy variables. IPv6 and other UDP are blocked. There is no direct fallback when the gateway or proxy fails. Host management, other applications and unrelated integrations keep their own routing.

The gateway currently requires an IPv4 SOCKS endpoint and a proxy permitting TCP to its DNS resolver (`1.1.1.1:53`). Proxies that block DNS forwarding will not work for hostname lookups. TCP applications, APIs and HTTPS are supported; QUIC, UDP-based applications, ICMP and native IPv6 are not. A proxied application must reach databases through its proxy or another explicitly designed network path. Changing a saved proxy does not silently rewrite running gateways; reapply application routing to use new credentials.

## Verification

Run `cargo fmt --all -- --check`, `cargo clippy --all-targets --locked -- -D warnings`, `cargo test --locked`, and `npm run check:ui`. Dedicated-host tests are in `tests/smoke.py`, `tests/runtimes.py`, and `tests/v2.py`. The v0.2 suite creates disposable tenants, verifies ZIP contents and both SQL restores, exercises S3 signatures/multipart/retry and pinned SFTP through authenticated SOCKS, and checks transparent PHP egress with a failed-proxy case. It does not contact a real Telegram chat or issue a third-party certificate.
